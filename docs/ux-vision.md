# oneAgent 用户体验愿景

> 本文档从用户心理层面分析 oneAgent 的核心价值主张，作为产品设计和功能优先级的指导参考。

## 用户画像：谁在用 oneAgent？

oneAgent 的目标用户是 **"以输出文档/内容为目标的知识工作者"**，包括但不限于：

| 用户类型         | 典型产出物                     |
| ---------------- | ------------------------------ |
| 开发者           | 代码、技术文档、API 规范       |
| 策划/产品经理    | 策划案、PRD、竞品分析报告      |
| 研究员/分析师    | 研究报告、数据分析、调研文档   |
| 编辑/内容运营    | 文章、脚本、营销文案           |
| 行政/项目管理    | 会议纪要、进度汇报、流程文档   |

他们的共同特征：

- 日常工作产出以 **结构化文档** 为主（而非即时通讯或口头交流）
- 对内容的 **准确性和可追溯性** 有要求
- 希望 AI 是"帮我干活的助手"，而非"替代我的机器"
- 追求"工具为我服务"而非"我适应工具"
- 对数据隐私有一定敏感度（尤其是涉及内部资料时）

## 用户画像补充：部门推广/管理员视角（你想“卖给部门”时绕不过）

当 oneAgent 的目标从“个人效率”升级到“部门级分发”，你会同时面对一类 **隐形决策者**（IT/安全/运维/采购/主管）。他们不关心“爽不爽”，关心“稳不稳、可不可以控、出了事谁背锅”：

| 角色 | 他们在意什么 | 体验/产品要求（可落地） |
| --- | --- | --- |
| IT/运维 | 安装/升级/回滚是否简单 | 单包分发、版本可追踪、诊断工具完备（doctor） |
| 安全/合规 | 数据是否出域、是否可审计 | 清晰的数据边界、关键行为留痕、可导出的审计线索 |
| 主管/采购 | ROI、稳定性、可复用资产 | SOP/Skills 资产化、模板化交付、可衡量的产出提升 |

这意味着：UX 不仅服务“操作顺滑”，还要服务 **“可被信任地推广”**（可诊断、可审计、可复现）。

## 真实需求的三层剥洋葱

### 第一层：表象需求 (他们说的)

> "我需要一个能帮我写东西的 AI。"

无论是代码、报告还是策划案，这是最肤浅的层次，任何 LLM 都能做到。

### 第二层：行为需求 (他们做的)

> "我明明可以用 ChatGPT/Cursor，为什么还要折腾本地部署一个 oneAgent？"

**这是关键问题。** 答案揭示了真实需求：

1. **控制感 (Control)：** 他们不是不信任云服务，而是 **害怕失控**。代码是心血，把核心资产交给黑盒感觉像"把命交给别人"。本地部署让他们觉得"掌控在我手里"。

2. **专属感 (Ownership)：** 他们希望 AI 是 **自己的**，是"我调教出来的"。通用 AI 是别人的产品，本地 + Skills 是自己的私人助理。

3. **无打扰 (Uninterrupted Flow)：** SaaS 产品有登录过期、有网络波动、有 Rate Limit。他们追求的是 **沉浸式开发心流**，任何"Loading..."都是对心流的谋杀。

### 第三层：情感需求 (他们不会说的)

> "我想要一个比我菜但比我勤快的'小弟'。"

这才是 **最深层次** 的用户画像：

- **不是替代我，是帮我扛活：** 他们不想被 AI 取代，他们希望 AI 做那些 **脏活累活**——跑测试、改格式、搜集资料、整理数据——而他们负责决策和核心创意。AI 是"实习生"，不是"总监"。

- **能让我安心睡觉：** 后台任务队列的本质不是"后台运行"，而是 **信任**。用户的真实渴望是："我下达指令后，可以不再焦虑地清空大脑"。这需要：
  - 不用盯屏幕 → 后台执行
  - 不用担心它瞎搞 → Workspace 边界 + Outcome Observer
  - 不用担心它失忆 → Resume 断点续传

- **能让我在同事面前有面子：** 这个需求最隐秘。使用 oneAgent 的人，往往是团队里"尝鲜"的那个。他们希望工具 **稳定且可展示**。如果演示时崩溃或出错，会很丢脸。因此，**可靠性 > 功能丰富性**。

## "爽"的体验公式

> **爽 = 控制感 × 信任感 × 存在感**

| 维度       | 用户心理                         | 实现方式                                                                 |
| ---------- | -------------------------------- | ------------------------------------------------------------------------ |
| **控制感** | "我知道它在干什么，边界在哪里"   | Workspace 清晰可见、边界明确；AI 改了什么文件一目了然；所有动作可回溯。 |
| **信任感** | "它不会害我，出了问题能补救"     | TDD/Observer 验证，用"证据"而非"口头保证"；Resume 给我"它不会害我"的底气。 |
| **存在感** | "它懂我，像一个被我培养出来的人" | Skills 让 AI "懂我"；历史记忆让 AI "记得我"；它越来越像"我的 AI"。      |

## 信任感的底座：纵深防御安全（Defense in Depth）

oneAgent 是“能改你本地文件、能跑你本地命令”的助手。要做到“我敢让它挂机干活”，以及能被 IT/安全/运维放心推广，安全不能只靠一句“请谨慎使用”，而要做成**多层、可审计、可降级**的系统能力：某一层失效时，其它层仍能兜底，避免单点失控。

下面是 oneAgent 的纵深防御分层（从外到内）：

| 层级 | 防御措施（方向） | 类型 |
| --- | --- | --- |
| 1. 入口控制 | 设备/客户端配对发 token、token allowlist；按 principal 分组/门控（管理员可回收） | 硬隔离 |
| 2. 身份验证 | Gateway Bearer token（可扩展 password/SSO）；关键入口显式风险提示 | 硬隔离 |
| 3. 外部内容包装 | 对 web/邮件/剪贴板/外部文件等“非可信内容”做边界标记与 UI 警告，降低 prompt injection 风险 | 软隔离 |
| 4. 可疑模式检测 | 对注入/外传/破坏性指令等模式做正则检测 + 记录到 trace/receipt，必要时触发阻断或二次确认 | 监控 |
| 5. 模型选择 | 默认推荐安全对齐更强的模型；高风险工具只在“安全档位”模型下启用（可由管理员策略放开） | 软隔离 |
| 6. 工具权限 | per-principal allow/deny；命令 profile（readonly/dev/full）；全局 kill-switch；决策可解释可审计 | 硬隔离 |
| 7. 沙箱隔离 | 对 `bash/run_command` 等高风险执行提供可选 sandbox（例如 Docker）+ 文件系统隔离（workspace 挂载/只读） | 硬隔离 |
| 8. 网络隔离 | 默认 loopback；跨设备访问优先 Tailscale（或显式开启 LAN 暴露并强提示风险） | 硬隔离 |

> 目标不是“绝对安全”，而是：默认安全、可控地放开、事后可追溯。

## 把愿景变成可验证的指标（否则很难判断“是否真的更好用”）

建议在设计/迭代时引入少量“可量化”的北极星指标，避免只靠主观感受：

- **TTFV（Time To First Value）**：首次安装到完成第一个可交付产物的时间（目标：分钟级）
- **Autonomy Rate**：用户下达一次指令后无需盯屏幕即可完成的比例（目标：逐步提升）
- **Trust Evidence Coverage**：每次交付是否都有可复核证据（diff / 测试报告 / 产物路径）（目标：默认提供）
- **Recovery Rate**：失败/中断后能否断点续传并最终完成（目标：可恢复 + 可解释）
- **Security Defaults Coverage**：默认安全配置的使用比例（token auth、最小权限策略、非公网暴露）（目标：默认=高）
- **Security Alert Rate**：可疑模式检测触发率与“被解释/被处理”的比例（目标：可见但不过度打扰）

## 工业级平台愿景：工作流化的多 Agent 系统（FastGPT/N8N + “每个节点都是 Agent”）

oneAgent 的长期愿景不是“一个会聊天的 Agent”，而是一个 **工业级 Agent 大平台**：像 FastGPT / N8N 一样拥有可编排的工作流，但工作流里的每一个节点都不是简单的函数/插件，而是一个 **类似 Claude Code / OpenAI Codex 那样的工作型 Agent**，能在自己的范围内完成一个可交付的小任务。

这类平台的关键在于：**节点之间传递的不只是文本，而是可追溯的交付物（常常是多个文件）**；以及每个节点都有稳定的“完成判定”，否则就会变成永远跑不完的聊天。

### 节点交付物：文件集（Artifacts）而非单段文本

- 一个节点的交付物可能包含多个文件（例如：`draft.md`、`sources.json`、`outline.md`、`figures/`、`diff.patch`）。
- 交付物必须有明确的“清单/索引”（manifest，best-effort），让下游节点可以基于路径、结构和证据消费，而不是把长文本复制粘贴到 prompt 里。
- 交付物与过程证据要绑定：让用户/审查者能“一眼打开”并看到依据（diff/test_report/trace 等）。

### 双层完成标准：客观验收（Hard）+ 主观评价（Soft）

工业级平台里，一个节点“完成”的判定应当分两层，否则会出现要么放水、要么卡死：

1) **客观验收（Hard Gate）**：可用代码/规则校验的事实
- 例如：文章字数达到 1 万字；目录结构齐全；引用条目数；代码通过 `go test`；格式化通过 lint；产物文件存在且路径稳定。
- 这层应尽量自动化并产出报告文件（test_report / validation_report），作为后续审查与回归对比的证据。

2) **主观评价（Soft Gate）**：只能用模型或人来判断的质量维度
- 例如：文风是否贴合作者偏好、逻辑是否流畅、是否“像人写的”、是否过度啰嗦、是否符合品牌调性。
- 这层应当用 **预设维度 + 打分阈值 + 结构化反馈** 的方式执行（best-effort），避免“凭感觉”。

> 风险提示（best-effort）：主观评分天然有不稳定性，必须可审计、可回放、可设置预算/迭代上限，并支持人工 override；否则容易出现“自评自嗨/刷分”或无限循环。

### 秘书：系统级中层领导（Orchestrator），把自然语言委托变成并行工作流

用户的真实工作不是线性的：写文章没写完，又要写脱口秀，再来写代码。工业级平台必须支持 **多线并行的工作编排**，而不是要求用户“一个任务做完再说”。

我们希望“秘书”成为系统级能力：
- **收任务**：接住用户不断变化的委托与上下文（不要因为用户插新需求就打断旧任务）。
- **搭流程**：把委托拆成节点（Agent workers）并编排依赖关系（隐式 workflow → 显式 workflow）。
- **派活与跟踪**：为每条工作线分配 worker agent，管理优先级/资源/预算，输出进度与下一步。
- **交付与验收**：按 Hard/Soft Gate 判定节点完成；通过后把交付物递交给下游节点；不通过则在节点内迭代修订。

### 为什么我们现在做的“地基”没有白费

当工作流里每个节点都是会写文件、会跑命令的 Agent 时，“能不能放心交给它”取决于基础设施，而不是 UI 文案：
- **安全与权限**：每个节点/worker 必须在可控权限下执行（最小权限、显式提权、可审计）。
- **可观测性**：每个节点必须留下证据（trace、diff、产物指针、失败原因）。
- **可回退性**：失败可恢复、误改可回滚；否则工业级平台不可推广。

## 极致场景想象

### 场景：大规模依赖替换

**用户说一句话：** "帮我把这个 monorepo 里所有 `lodash` 的用法替换成 `radash`。"

**一个"爽"的体验是：**

1. AI 先问："我检测到了 `packages/core`, `apps/web`, `apps/mobile` 三个地方有 `lodash`，要全换还是只换 core？" **(控制感)**

2. 用户说"全换"，然后去吃饭。

3. 一小时后回来，看到一个报告："已完成，157 个替换，测试全绿。这是 diff 和测试报告。" **(信任感)**

4. 下次用户提类似需求，AI 说："上次你让我换 radash，这次也用同样方法吗？" **(存在感)**

### 场景：多线程委托给“秘书”（写文章 / 写段子 / 写代码并行推进）

**用户不断插入需求：**
1. "写一篇 1 万字文章，文风偏克制、理性。"
2. "我突然要上台，帮我写 5 分钟脱口秀。"
3. "顺便把这个 repo 的测试跑通并修掉 3 个失败用例。"

**一个工业级的体验是：**
1. 秘书把它们拆成 3 条工作线：文章写作（多文件交付）、段子（短交付）、代码修复（有测试证据）。**(控制感)**
2. 三条线并行推进，UI 中每条线都有明确进度、预计时间、产物入口与风险提示。**(存在感)**
3. 代码线以测试全绿作为 Hard Gate；文章线以“字数/结构”Hard Gate + “文风/逻辑”Soft Gate 作为完成判定。**(信任感)**
4. 任意一条线失败不会拖死其它：可 resume、可降级、可回滚，且失败原因可追溯。**(信任感)**

### 场景：撰写季度汇报 (非开发者)

**用户说一句话：** "帮我根据这个月的销售数据，写一份 Q4 季度汇报。"

**一个"爽"的体验是：**

1. AI 先问："我看到 workspace 里有 `sales_oct.xlsx`, `sales_nov.xlsx`, `sales_dec.xlsx`，要合并分析还是分月呈现？" **(控制感)**

2. 用户说"合并，重点突出同比增长"，然后去开会。

3. 半小时后回来，看到："已完成 `/output/Q4_Report.md`，包含 3 张图表和执行摘要。" **(信任感)**

4. 用户说"帮我转成 Word"，一键导出 `Q4_Report.docx`。 **(最后一公里)**

### 场景：首次使用

**一个"爽"的开箱体验：**

```bash
# 一行启动，浏览器自动打开，workspace 已锁定当前目录
oneagent serve --workspace . --open
```

进入界面后：

- 不需要配置模型（有默认）
- 不需要输入路径（已从命令行传入）
- 页面上方清晰显示："当前工作目录：/Users/me/myproject"
  - Windows 场景下默认自带 Git/Git Bash，命令执行仅支持 bash（其它 shell 直接报错，避免体验分裂）

用户的 first impression："它知道我要干什么。"

## 功能优先级指导

基于上述分析，功能优先级应遵循：

1. **可靠性 > 功能丰富性**：宁可功能少，不可崩溃或出错。
2. **边界清晰 > 能力强大**：用户宁可 AI 说"这个我做不了"，也不想看到它乱改文件。
3. **无感启动 > 深度配置**：开箱即用比"高度可配置"更重要。
4. **结果可信 > 过程炫技**：用 TDD/Observer 证明结果，比"我用了最新模型"更有说服力。

## 未来能力愿景：最后一公里

对于非开发者用户，AI 产出的 Markdown 文档往往不是最终交付物。他们需要的是能直接发给领导、客户、合作伙伴的 **Office 格式文件**。

### 愿景：一键导出 Office

| 源格式     | 目标格式        | 场景                         |
| ---------- | --------------- | ---------------------------- |
| `.md`      | `.docx` (Word)  | 报告、策划案、会议纪要       |
| `.md`      | `.pptx` (PPT)   | 演示汇报、培训材料           |
| `.csv/.md` | `.xlsx` (Excel) | 数据报表、预算表             |

### 实现路径

1. **基础能力**：集成 `pandoc` 或类似工具，支持 Markdown → DOCX/PPTX 转换。
2. **模板支持**：允许用户上传公司模板 (`.dotx`/`.potx`)，AI 按模板样式输出。
3. **样式映射**：将 Markdown 的 `#`, `##`, `-`, `>` 等语法映射为 Office 的"标题1"、"标题2"、"项目符号"、"引用"等样式。
4. **交互式调整**：用户可以在 UI 中预览并微调格式，再导出。

### 为什么重要？

> "帮我写一份报告" 和 "帮我写一份**能直接发出去的**报告" 是两回事。

后者才是真正的价值闭环。如果用户还需要手动复制粘贴到 Word、调格式、加页眉页脚，那 AI 只是"半成品助手"。
